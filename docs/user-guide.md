# 利用方法（運用・モデル・終了・回復）

## PCと保存先の登録

初期セットアップの流れ（Windowsでの情報取得、FedoraでのMOK登録・PC登録、PAIR BOOT起動）については [quick-start.ja.md](quick-start.ja.md) を参照してください。

まず、候補PCのWindows上でそのPCの情報が記載された候補JSONファイルを生成して保存します。このファイルを同じPCで起動したFedoraで照合・確認してUSBに登録します。PC登録一覧の本体はGPU-LOGSのgpu-config/registry.jsonです。複数USBでは台帳を回収・マージし、管理GUIの配布操作で各USBへ反映してhostsフォルダ内のファイルも再生成します。登録情報を手入力で流用してはいけません。

USBを書き直す場合のバックアップと台帳の復元は、[USBを書き直す前のバックアップ](#usbを書き直す前のバックアップ)を参照してください。

### 1台の管理PCで台帳をまとめる

回収・マージ・配布は1台の管理PCでできます。その管理PCの登録、NVIDIA GPU、PAIRの起動は不要です。PAIRを起動する予定の新規のPC登録を行うには、対象PCのFedoraでの実機確認が必要です。

| 操作環境 | 対応と制限 |
| --- | --- |
| Windowsのファイル操作 | 各USBの `GPU-LOGS/gpu-config/registry.json` を別名でコピーして回収・バックアップできます。統合や起動用hostsの再生成には管理ツールを使います。 |
| Windows管理GUI／PowerShell版 | 通常GPUとGPUなしTESTの台帳を回収・マージ・配布できます。0.9.0→0.9.1の対応する版変換も扱います。管理作業のためにFedoraを起動する必要はありません。[Windowsでの操作手順](windows-fleet.md)を参照してください。 |
| Fedora管理GUI | GPUなしTESTと対応する版変換を含めて処理できます。操作対象は、そのFedoraを起動したUSBのGPU-LOGSに限定しています。別USBへの配布では、同じ管理PCで配布先USBのFedoraを起動します。 |

Fedora管理GUIでは次の順に行います。

1. 必要な各台帳を別名のJSONとして回収します。Windowsでコピーしても構いません。管理PC上に元の控えを保持します。
2. 統合に使うUSBのGPU-LOGSへ回収JSONをコピーし、そのUSBからFedoraを起動します。
3. 「複数の台帳JSONをマージ」で統合元の台帳と統合後の保存先ファイル名を指定します。新しい世代番号は、統合元のすべての台帳の世代番号より大きくします。
4. 内容を確認した統合JSONを各配布先USBのGPU-LOGSへコピーします。複数USBから起動するときは、どれを起動したか確認してください。
5. 配布先USBから同じ管理PCをFedora起動し、「統合台帳をこのUSBへ配布」でそのJSONを選択します。必要なUSBごとに繰り返します。

配布操作は台帳と起動用hostsを更新します。`registry.json` だけを直接上書きする方法で代用しません。版・世代・期限・保存先・安全性の不一致は停止条件です。移すだけで確認日を延ばしたり、既存登録の保存先を勝手に変えたりはしません。0.9.0→0.9.1は対応する移行ですが、任意の版の混在を許可するものではありません。

台帳を他のUSBへ配っても、root・state・Modelsはコピーされず、登録済みのNTFS保存先も変わりません。MOKは各PCのfirmware側の登録であり、台帳の配布では移りません。

## root・state・Models

選択したNTFS領域の既定フォルダはGPU-Linuxです。登録時に変更できます。root.img、state.img、各管理用metadata、Modelsを使用します。0.9.0ではrootは6GiB、初期stateは1GiBです。初回コピー用に合計7GiBと1GiB以上の予備容量を用意し、更新・回復・キャッシュには追加の空き容量を確保します。初回Normal起動でフォルダを作らせ、正常終了した後でモデルをコピーする順序を推奨します。root.img、state.imgや管理ファイルをモデルコピーの際に上書きしないでください。

/modelsは登録先のModelsを読み取り専用で公開します。画像モデルのGGUFとmmprojは対応する組み合わせをモデルごとのサブフォルダへ置きます。mmprojのファイル名はmmprojで始めます。モデルを追加したら推論エンジンを再起動して一覧を確認します。

開発者PCでもPAIRを起動し、推論ノードと同じクラスタへ参加させます。通常のllama.cpp接続先は、その開発者PCの http://127.0.0.1:8080/v1 です。APIに送るモデル名は/v1/modelsで確認します。モデル名、コンテキスト上限、画像・ツール対応はクライアント設定と実際のエンジンを揃えます。

開発ツールの設定と動作確認は[共通準備](pair-client-setup.md)、[VS Code](vscode-pair-parallel-quick-start.md)、[OpenCode](opencode-pair-parallel-quick-start.md)を参照してください。子エージェントの並行実行と、PAIRが実際にどのノードへ要求を振り分けたかは分けて確認します。

### USBにroot.imgやModelsを保存する場合

PC本体にC:以外の領域がない場合などは、利用者が用意したUSBのNTFSデータ領域を保存先に指定できます。

起動USBの未使用部分に利用者が追加した第5パーティションも、利用者自身のデータ領域です。PAIR BOOT専用の領域ではなく、保存する内容は利用者が決めます。利用例として、十分な空き容量があればroot.imgやstate.imgなどの保存先にも指定できます。

初回コピーには両イメージの合計7GiBと1GiB以上の予備容量が必要です。Modelsも同じ領域に置く場合は、モデルの大きさに応じた追加容量が必要です。起動USBにこれらをまとめて保存するには、USBイメージ自体の約8.4GBに加えて、その空き容量を確保します。32GB以上のUSBでも、モデルの大きさによっては収まらない場合があります。

1. Windows管理GUIで保存先のUSB上のNTFSドライブとフォルダを選び、「USBをroot保存先に指定」にチェックして候補JSONを保存します。
2. Fedora Liveで保存先NTFSが自動マウントされている場合は、使用中のファイルを閉じ、そのNTFS領域だけを安全にアンマウントします。GPU-LOGS・GPU-FEDORAやUSB全体は取り外しません。
3. 管理GUIの「Windows候補から保存先・GPUを登録」で候補JSONを選び、保存先とGPUを確認して登録します。別途取得したBitLocker確認JSONがある場合は、「別の観測JSONを選択する」から指定します。
4. [クイックスタートの起動手順](quick-start.ja.md#4-pair-bootを起動する)に従って起動します。保存先に使うUSBは、終了まで接続したままにしてください。

## USBを書き直す前のバックアップ

同じUSBへ全体イメージを書き込むと、パーティション表も置き換わります。利用者が追加した第5パーティションを含め、USB上の既存データは保持される前提にしないでください。

書込み前に、利用者自身がUSB内の必要なファイルを確認し、別のドライブへバックアップしてください。第5パーティションには任意のデータを保存できるため、内容を決めつけて自動でバックアップすることはありません。root.img・state.img・Modelsを置いている場合は、それらと管理用ファイルを含む保存先フォルダもバックアップします。root・stateを利用中の場合は、PCを正常終了してから行います。

PC登録情報を引き継ぐ場合は、候補JSON、BitLocker確認JSON、台帳もバックアップします。台帳の復元は、バックアップした台帳を別名でUSBへ置き、管理GUIの配布操作を使います。古いusb-config.json、証明書、gui、toolsで新USBを上書きしません。

## 設定の保持とroot交換

ロゴは表示時の端末幅に合わせて横幅を調整します。起動直後とPAIR終了後で画面の列数が変わっても、その時点の幅で描画します。

起動を停止した場合は、空行と区切り線で囲まれた `PAIR BOOT - STARTUP STOPPED` の理由と対処を確認します。`THIS PC IS NOT REGISTERED FOR THIS USB` は、このPCの登録がUSBにないことを示します。Fedora Liveで保存先とPCを登録してください。`NVIDIA HARDWARE DETECTED IN TEST MODE` は、NVIDIA機器があるPCでTESTを選んだことを示します。FedoraでGPU登録を確認し、対応するNormalまたはUnlockを選び直してください。

`Details:` 以下には元のエラーを残します。root設定処理のエラー表示はメンテナンス用プロンプトの直前に再表示します。表示の変更によって安全確認を省略したり、自動で別モードへ切り替えたりはしません。

0.9以降はrootとstateを分けて保存します。0.8以前からの自動設定移行はありません。既存データを残し、新しい保存先フォルダへ登録してください。

PAIRの設定・クラスタ情報・起動ON/OFFとホームはstate.imgに保存します。PC固有のLinux識別情報もstateへ保存します。PAIR本体と固定llama.cppはroot内の/optにあり、設定領域に実行ファイルを持ち越しません。stateにはPAIRが生成する秘密情報も入るため、Gitやログ添付へ追加しないでください。module署名用の秘密鍵はstateへも置きません。

起動バナーには現在のrootの版と実際のNormal/Unlockを表示します。PAIRを終了して3択メニューへ戻った場合も再表示します。

0.9.1ではroot revisionで更新方向を判定します。0.9.0のrootはrevision 0、0.9.1の現在の構築はrevision 3です。USB側が新しければ、安全確認・容量確認・コピー検証後に自動更新します。旧rootとreceiptをroot-before-update-*へ保存し、stateとModelsは保持します。同じrevisionでSHAが異なる場合は採番不整合として停止します。通常利用によるrootの書込みではなく、receiptに記録した配布元SHAで比較します。

USB側のrevisionが古い場合は、コンソールに次の選択を表示します。

1. 古いrootへ交換して起動する。追加で `DOWNGRADE` の入力が必要です。
2. 現在のrootを保持して起動を試みる。kernel、boot ABI、GPUドライバ、gpu-unlock、state schemaが適合する場合だけ選択できます。
3. 電源を落とす。Enterや入力終了時もこの選択です。保存先を安全に閉じてから電源断を要求します。

対応しないstate形式への交換は許可しません。現行の対応範囲はstate schema 1です。古い0.9.0 USBにはこの新処理がないため、0.9.1のrootで0.9.0 USBを使った場合は従来どおり停止し、選択画面は出ません。


旧rootを残すことだけではrollbackの保証になりません。新版PAIRがstateの形式やクラスタ状態を更新した場合、旧rootでそのまま利用できないことがあります。状態のbackup/復元はクラスタとの整合性も含めて判断します。

PAIRは専用サービスでgpuユーザーとして実行します。終了時にサービスの子プロセスも終了させます。後片付けを確認できない場合は再起動を拒否します。PAIR内部のサービスが異常終了しエンジン操作ができなくなった場合は、一度PAIRを終了してメニューから再起動します。それでも起動を拒否されたらPCの正常な再起動を行い、原因を確認してください。

固定エンジンの更新はroot交換で行います。PAIRからの固定エンジンのアンインストールは管理領域外として拒否されます。

## 終了とUSBの取り外し

現在の構成ではPAIRの操作画面をtty1、保守用の物理rootコンソールをtty2に配置します。保守コンソールにはパスワードを設定していません。対象PCの物理アクセスを管理できる環境で使用します。SSHログインは既定で無効です。

PAIRをqで終了すると、PAIR再起動、PC再起動、電源断のメニューへ戻ります。完了前に電源を強制的に切らないでください。

root revision 3では、dracutが先に解除したloopを終了処理で再解除して停止する問題を修正します。解除済みをカーネルへ照会し、接続中なら解除後の完了も確認してからNTFSの終了処理へ進みます。状態不明・使用中・同期やアンマウントの失敗では自動電源断を止めます。旧revisionから更新した場合は、バナーの `Root rev: 3` を確認し、メニューの再起動・電源断を実機で確認してください。

USB CAN BE REMOVED NOWの表示がある場合のみ起動USBを取り外せます。root/Modelsを保存する別USBは接続したままにします。Fedora Liveの起動USBは稼働中に取り外しません。

## 停止・回復

安全性を確認できない保存先や、登録のないPCでは停止します。BitLockerや高速スタートアップの状態、PC識別情報、選択した領域を確認します。確認できない状態をOff等に手入力して通さないでください。

root.imgまたはstate.imgの回復が必要な場合は、元を保持しコピー上でfsckします。追加の容量が必要です。回復できない場合や取引が中断した場合は停止し、Fedoraで確認します。root-backup-*、state-backup-*、.root-maintenance.*、.state-maintenance.*、.root-replace.*、receiptを理由なく消さず、元イメージを保持します。NTFSをマウント中のrootイメージへ手動でfsckしません。

ログを共有するときはUUID、ホスト名、ネットワーク、登録情報等を除いた必要な部分に絞ります。鍵や認証情報は共有しません。
